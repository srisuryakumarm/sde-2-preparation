## Part 1 — Requirements (Step 1)

The client-perceived guarantee a payment system needs is **exactly-once processing** — a retried request (network timeout, ambiguous response, a client's own retry logic firing) must never result in two charges. The honest mechanism underneath that promise, stated precisely rather than left vague: **at-least-once delivery, made safe by idempotent processing** — the same phrase Day 131's job scheduler will name formally tomorrow, already true here today. Additionally: every transaction must be auditable after the fact — "how did this balance get to be what it is" needs a real, provable answer, not just trust in whatever a mutable column currently says.

## Part 2 — Idempotency Keys

### The shape, generalized

Every prior appearance of "check before acting" in this series checked **existence of a resource** (has this ID been claimed, has this seat been held). Idempotency keys check something subtly different and more general: **has this exact logical intent already been fully processed** — regardless of how many times the request carrying that intent has physically arrived.

### Definition

A unique key, generated by the **client**, once per logical user action — not once per HTTP attempt. The server checks whether it has already fully processed that exact key before doing anything at all, and if so, returns the *original* stored result instead of re-executing.

> 🔑 **Key Takeaway:** the key must represent *intent*, not *attempt*. If "user clicks Pay" generates one key, and a network timeout causes the client's retry logic to resend the same request, the retry must reuse the **same** key. Generating a fresh key per retry defeats the entire mechanism — and is, in practice, the single most common real bug in idempotency-key implementations.

### Mechanism, step by step

1. Client attaches idempotency key `K` to the payment request.
2. Server checks an idempotency store (Redis) for `K`.
3. **Not found:** atomically claim `K` (mark it `in-progress`), *then* actually process the payment, *then* store the result (`completed`, plus the response payload) against `K`, with a bounded TTL — 24 hours is a reasonable default; a "retry" arriving six months later is realistically a new attempt, not a duplicate of the original intent.
4. **Found, `completed`:** return the *stored* result immediately. Do not reprocess.
5. **Found, `in-progress`:** a genuinely concurrent duplicate arrived while the first attempt is still being processed — return "still processing," never let a second attempt proceed to charge.

### Why the claim step must be atomic

Case 5 above is exactly why "check, then set" can't be two separate steps: if two identical requests both check at the same instant, both see "not found," and both proceed to charge, the mechanism has failed at the one moment it existed to prevent. The claim itself needs the same atomic test-and-set shape Day 121 already established — here, most naturally, `SETNX` on the idempotency key itself.

### When to reach for it

Any operation with a real-world side effect — charging money, shipping a package, permanently decrementing inventory — where the client might legitimately retry and a duplicate execution is a genuine bug, not merely wasted work.

### Why not just make the operation itself idempotent?

Some operations are naturally idempotent already — "set balance to $340" repeated twice changes nothing. "Charge $50" is **not** naturally idempotent — charging it twice is a materially different outcome from charging it once. Idempotency keys are the general-purpose mechanism for making an operation that is *not* naturally idempotent *behave* idempotently from the caller's perspective, without requiring the underlying business action to have that property itself.

> ⚠️ **Common Mistake:** keying the check only on *who* is asking, not *what* they're asking for. If a client bug reuses the same key for two genuinely different payment amounts, the server should detect and reject that mismatch explicitly — storing a hash of the original request payload alongside the key, and comparing it on reuse — rather than silently returning the *first* amount's cached result for a *different* request.

## Part 3 — Distributed Locks via Redis `SETNX`

### Definition

A mechanism ensuring only one process, across **multiple separate server instances**, can hold the right to proceed on a specific logical resource at a time — the genuine multi-machine generalization of Day 124's `synchronized`, which only ever protected a single JVM.

### Mechanism

```
SET lock:order:123 <unique-token> NX PX 30000
```
`NX` — set only if the key doesn't already exist, a single atomic Redis command, immune to racing with itself. `PX 30000` — auto-expire after 30 seconds, so a crashed holder doesn't deadlock every other process forever. The `<unique-token>` (a UUID generated fresh by the acquiring process) is the detail that makes release *safe* — see below.

### The unsafe-release bug, traced in full — this is the correctness claim, proven, not asserted

1. Process A: `SET lock NX PX 30000 tokenA` succeeds — A holds the lock.
2. A stalls — a long GC pause, a slow network hop — for 35 seconds, past the 30-second TTL.
3. Redis auto-expires the key at 30s. A has no way to know this happened yet; it's still stalled.
4. Process B: `SET lock NX PX 30000 tokenB` succeeds (the key was gone) — B now legitimately holds the lock.
5. A finally wakes up, finishes its (now-stale) work, and — if it naively calls `DEL lock` without checking the value first — **deletes B's active lock**.
6. Process C: `SET lock NX ...` succeeds (the key is gone again) — C now *also* holds the lock, at the exact moment B still correctly believes it holds it.
7. **Result:** B and C are now both proceeding concurrently on what was supposed to be mutually exclusive access — precisely the bug distributed locking exists to prevent, reintroduced through an unsafe release.

### The fix

Release must be "if the current value at this key is still *my* token, delete it" — as **one atomic operation**, via a Lua script, not two separate Redis calls (a `GET` followed by a `DEL` leaves a window where another process could acquire the lock in between). This is Day 121's Lua-atomicity pattern again, applied to release rather than acquire — the same mechanism, a genuinely new place to use it.

> 💡 **Interview Insight:** naming the unsafe-release bug *unprompted*, before an interviewer asks "but what if the lock expires while you're still working," is exactly the kind of "say it before it's asked" habit Day 128's mock was built to train.

### Extension material — Redlock (marked, not core to today's required depth)

A single Redis instance is a single point of failure for the lock's own guarantee — if that one instance has a replication or failover hiccup, the safety property can be violated even with correct token-based release. **Redlock** acquires the lock across a **majority** of several independent Redis instances — Day 125's Quorum concept, reapplied to locking rather than replicated data — before considering it genuinely held. Worth knowing this exists and why; not required to implement it for today's stub.

### Idempotency keys vs. distributed locks — genuinely different jobs

| | Idempotency key | Distributed lock |
|---|---|---|
| Prevents | The *same* logical request being processed twice, even long after the first completed | *Different*, genuinely concurrent requests touching the *same* resource at once |
| Triggered by | A retry of one specific intent | Any two independent operations racing on one resource |
| Example here | A retried "pay $50" request | A "process payment" and a "cancel order" call landing on the same order at the same instant |

A real payment system needs **both** — they guard against two different failure shapes, and neither substitutes for the other.

## Part 4 — The Double-Entry Ledger

### Definition

Every transaction is recorded as at least two balanced entries — a **debit** to one account and a **credit** to another, of equal magnitude — such that the sum of every entry in the entire system, at any moment, is exactly zero.

### Mechanism

Rather than a single mutable "balance" column updated in place, the ledger is an **append-only log of entries**. An account's current balance is *derived* — the sum of all its entries — not stored as raw ground truth (a cached, materialized balance column for fast reads is common in practice, but it's explicitly a cache of a derivable value, not the source of truth itself).

**A worked example:** a customer pays $50 for an order.
- Entry 1: debit "Customer Payment-Owed," $50.
- Entry 2: credit "Platform Revenue," $50.
- Sum across both entries: $50 − $50 = 0.

### Why it's self-checking, concretely

Because every entry has an equal-and-opposite twin, the total across the *entire* ledger must always sum to exactly zero. If it ever doesn't, that's an immediate, provable signal that something is wrong *somewhere* — not a discrepancy someone has to go hunting for blind.

> 🔗 **Forward reference:** tomorrow's `@Scheduled` reconciliation job (Day 131) is a direct, concrete application of exactly this property — it isn't a separate idea, it's this one, automated.

### Why not a single mutable balance field

- **No audit trail.** An in-place update destroys history; "how did this balance get here" has no real answer once it's overwritten.
- **Concurrency.** Two concurrent updates to the *same* mutable field need real locking discipline to avoid a lost update (the optimistic/pessimistic locking precedent from Day 117). An **append** has no equivalent race at all — two concurrent debits simply become two independent new rows, both preserved, both correctly counted, with no lost-update risk even under heavy concurrency.

### Trade-off, and the one hard rule

Computing a live balance by summing potentially many historical entries costs more than reading one field directly — mitigated in practice by periodically materializing a cached running balance, with the append-only log remaining the actual source of truth for audit and reconciliation.

> ⚠️ **Common Mistake:** allowing an *unbalanced* write at all — a code path that writes a debit without its matching credit. The entire self-checking guarantee depends on this never happening, which means the write itself must be a single atomic operation that commits both sides or neither.

## Part 5 — Estimation, HLD, Detailed Design, Bottlenecks (Steps 2–5)

**Estimation:** assume a normal sustained load of **500 payments/sec**, with a sale-event peak of **10x**, ≈5,000/sec. The idempotency store and lock service must be sized against the peak — a store that comfortably handles 500/sec but chokes at 5,000/sec fails exactly during the highest-stakes traffic moment, not a quiet Tuesday.

**HLD:** Client → Payment Service (idempotency check → lock acquire → charge → ledger write → lock release, in that order per the pseudocode below) → external Payment Gateway → async reconciliation (Day 131).

**Bottlenecks:**
- **The idempotency store and lock service are themselves new, critical single points of contention** — nearly every request now funnels through both, meaning their own availability and replication story matters as much as the payment logic itself. Worth stating this honestly rather than treating them as free infrastructure.
- **Extension material:** if the charge succeeds but the ledger write fails (or vice versa) across two separate systems, that's a real correctness gap — production systems typically close it with a single database transaction covering both, or a transactional outbox pattern for cross-system consistency. Flagged here as a real, known concern beyond today's required depth, not folded into the core design.

## Coding Exercise — Idempotency-Wrapper Pseudocode

```
function processPayment(request, idempotencyKey):
    existing = idempotencyStore.get(idempotencyKey)
    if existing exists:
        if existing.status == "completed":
            return existing.storedResponse        // duplicate — return prior result
        if existing.status == "in-progress":
            return "still processing, retry shortly"  // concurrent duplicate, don't proceed

    claimed = idempotencyStore.setnx(idempotencyKey, {status: "in-progress"}, ttl=24h)
    if not claimed:
        return processPayment(request, idempotencyKey)  // lost the race — re-check from the top

    lockToken = uuid()
    lockAcquired = redis.set("lock:order:" + request.orderId, lockToken, NX, PX=30000)
    if not lockAcquired:
        idempotencyStore.delete(idempotencyKey)   // release our claim; caller may retry
        return "order currently locked, retry shortly"

    try:
        result = chargeGateway(request)                 // the actual external call
        ledger.recordDoubleEntry(request, result)        // Part 4, atomically with the result
        idempotencyStore.set(idempotencyKey,
            {status: "completed", storedResponse: result}, ttl=24h)
        return result
    finally:
        releaseLockIfOwned("lock:order:" + request.orderId, lockToken)  // Lua: GET==token → DEL
```

## Day 130 — Interview Questions

**Q1. Why must the client, not the server, generate the idempotency key?** Only the client knows whether a given request is a fresh action or a retry of one already sent — a server-generated key on each incoming attempt would treat every retry as a brand-new intent, defeating the entire mechanism.

**Q2. What's the single most common real bug in idempotency-key implementations?** Generating a new key on every retry attempt instead of reusing the original key tied to the user's actual intent.

**Q3. Why does the mechanism need an explicit `in-progress` status, not just `completed` vs. `not found`?** Without it, two genuinely concurrent duplicate requests could both see "not found" and both proceed to charge — `in-progress` is what a second, racing request checks against to correctly back off instead.

**Q4.** [Trace] **Walk through the unsafe distributed-lock release bug end to end.** A holds a lock past its TTL due to a stall; the lock auto-expires; B acquires it legitimately; A wakes up and blindly deletes the key, removing B's active lock; C then acquires the same lock while B still believes it holds it — two processes now proceeding concurrently on what was meant to be exclusive.

**Q5. What's the specific fix for the unsafe-release bug?** Release must atomically check that the current lock value is still the releasing process's own token before deleting — via a single Lua script, since a separate `GET` then `DEL` leaves a race window.

**Q6. Why is a Redis `SETNX`-based lock preferred here over Day 124's `synchronized` block?** `synchronized` only protects against concurrent threads within a single JVM; a distributed lock is needed because the payment service runs as multiple separate instances, none of which share memory.

**Q7. What's the actual difference between what an idempotency key protects against and what a distributed lock protects against?** An idempotency key stops the *same* logical request from being processed twice, even long after the first completed. A distributed lock stops *different*, genuinely concurrent operations from touching the same resource at the same instant. Neither substitutes for the other.

**Q8. Why does the lock's TTL involve a genuine trade-off with no perfect setting?** Too short, and the lock can expire while the work is still legitimately in progress, letting someone else in prematurely (today's unsafe-release scenario). Too long, and a real crash leaves everyone else blocked longer than necessary. The right value is a judgment call grounded in expected work duration, not a fixed default.

**Q9. What is Redlock, and why would a system reach for it over single-instance `SETNX`?** Acquiring the lock across a majority of several independent Redis instances (Quorum, Day 125, reapplied) before considering it held — needed when a single Redis instance's own availability is itself an unacceptable single point of failure for the lock's guarantee.

**Q10. Why is an account's balance derived rather than stored directly in a double-entry ledger?** The append-only entry log is the actual source of truth; a stored balance column, where it exists for read performance, is explicitly a cache of what the entries already prove, not an independent fact.

**Q11. In what precise sense is a double-entry ledger "self-checking"?** Every entry has an equal-and-opposite twin, so the sum across the entire ledger must always equal exactly zero — any deviation is an immediate, provable signal of a bug, not something that needs to be independently discovered.

**Q12. Why is an append-only ledger safer under concurrency than an incrementable balance field?** Two concurrent debits against an append-only log simply become two independent new rows, both preserved correctly with no race; two concurrent increments against one mutable field risk a lost update without careful locking discipline.

**Q13. Of the four earlier appearances of "check-then-act" in this series (Days 121, 122, 124, 126), what's genuinely new about today's treatment rather than a repeat?** Today generalizes from "does this resource already exist" (the earlier four) to "has this exact logical intent already been fully processed, and can two truly concurrent copies of it be prevented from both succeeding" — combined, for the first time, with the ledger's own independent correctness guarantee.

**Q14. Why does a real payment system need both idempotency keys and distributed locks rather than just one?** They guard against different failure shapes — a retried request needs idempotency; two unrelated concurrent operations on the same order need mutual exclusion. A system with only one of the two is still vulnerable to the failure the other one prevents.

**Q15. What's a concrete real bug that idempotency-key mismatch detection specifically catches?** A client bug that reuses the same idempotency key for two requests with genuinely different payloads (say, two different charge amounts) — without payload comparison, the server would silently return the *first* request's cached result for a request that was actually asking for something different.
