## 2. Part 1 — Day 30 (2.5 h): Toolchain, annotations, and the Java bits Spring leans on

### 1.1 Maven, properly — **Must** (60 min)

**What:** Maven reads `pom.xml`, downloads libraries from Maven Central into `~/.m2/repository` (cached after the first download), compiles `src/main/java`, runs `src/test/java`, and packages `target/*.jar`.

**Layout is a convention, not a choice:** `src/main/java` (code), `src/main/resources` (`application.yml`), `src/test/java` (tests), `target/` (build output — never commit it).

**Anatomy of a Boot `pom.xml` (annotated):**

```xml
<parent>                                    <!-- 1. inherits version management for ~hundreds of libraries -->
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>4.1.x</version>                  <!-- the ONE place the Boot version lives -->
</parent>
<groupId>com.you</groupId>                  <!-- 2. your project's coordinates: groupId + artifactId + version (GAV) -->
<artifactId>spring-sandbox</artifactId>
<version>0.0.1-SNAPSHOT</version>
<properties><java.version>21</java.version></properties>
<dependencies>
  <dependency>                              <!-- 3. no <version> here: the parent's BOM supplies it -->
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-webmvc</artifactId>
  </dependency>
  <dependency> ... <scope>test</scope> </dependency>   <!-- test scope: on the classpath for tests only -->
</dependencies>
<build><plugins>
  <plugin> spring-boot-maven-plugin </plugin>          <!-- 4. repackages the jar so `java -jar` works ("fat jar") -->
</plugins></build>
```

- **Correction to the v1 micro-primer:** dependencies are *not* listed "by name and version" in an Initializr pom — starters have no version, because the parent supplies it. If you open your pom and see no versions, that is correct.
- **Starter** = a pom containing no code, only a curated, version-compatible list of other dependencies. `…-webmvc` ≈ Spring MVC + embedded Tomcat + Jackson.
- **`BOM`** = a list of "if you use library X, use exactly version Y". The parent is how you inherit Boot's BOM. (Day 62's `<dependencyManagement>` is the same idea, written by hand.)
- **Why `./mvnw`, not `mvn`:** Week 1 installed JDK, IntelliJ and Git — not Maven. The wrapper script in your project downloads the right Maven version and runs it.

| Command | Does |
|---|---|
| `./mvnw spring-boot:run` | compile and start the app |
| `./mvnw test` | compile, then run all tests (Day 45's exact command) |
| `./mvnw clean package` | delete `target/`, compile, test, build the jar |
| `./mvnw -DskipTests package` | same, skipping tests (use sparingly) |
| `java -jar target/<name>.jar` | run the packaged app — no Maven needed |
| `./mvnw dependency:tree` | show every library actually on your classpath, and why |

**Adding a dependency (you will do this ~15 times in this plan):** edit `pom.xml` → *Reload All Maven Projects* in IntelliJ → confirm with `./mvnw dependency:tree | grep <name>`.

**Exercise 1 (Must):** generate `spring-sandbox` at start.spring.io — Maven, Java 21, Jar, dependency **Spring Web** only. Keep it as a separate IntelliJ project (push it as `spring-primer/` inside `java-fundamentals` if you want it on GitHub). Then:

2. Run `./mvnw test`, then `./mvnw clean package`, then `java -jar target/spring-sandbox-0.0.1-SNAPSHOT.jar`.
3. Read the startup log once, top to bottom. Find: the Boot version, the active profile (`default`), `Tomcat started on port 8080`, `Started SpringSandboxApplication in … seconds`. Stop the app.
4. Run `./mvnw dependency:tree` and find Tomcat and Jackson in it.

### 1.2 Annotations and reflection — **Must** (30 min)

**What:** an annotation is metadata attached to code. `@Override` is read by the *compiler*. Spring's `@RestController`, JUnit's `@Test` and Hibernate's `@Entity` are read by *running code* through **reflection** — a program inspecting its own classes at runtime. (Day 34's book introduces this in one paragraph; today you do it once with your hands.) Day 62's custom `@LogExecutionTime` is exactly this mechanism.

**Declaring one:**
```java
@Retention(RetentionPolicy.RUNTIME)   // kept in the .class file AND visible at runtime (default is not)
@Target(ElementType.TYPE)             // may be placed on classes
public @interface Marker { String value() default ""; }
```

**Exercise 2 (Must, plain Java in `java-fundamentals`, no Spring):** annotate two classes with `@Marker`, leave a third unmarked. In `main`, loop over a hard-coded `List<Class<?>>`; for each class print whether `getAnnotation(Marker.class)` is present; for the marked ones create an instance with `getDeclaredConstructor().newInstance()` and call a method through a shared interface. You have just written the first 15 lines of a Spring container.

### 1.3 Lambdas, Streams, `Optional` — the 20 % you need — **Must** (45 min)

Day 17 used lambdas only as `Comparator`s. Spring code assumes three more things:

- **Lambda** = an implementation of an interface with one abstract method (a *functional interface*). **Method reference** `TaskResponse::from` is a lambda shorthand.
- **Streams** — a pipeline over a collection that does not modify it. The four operations you will use: `filter`, `map`, `toList()`, `findFirst()` (plus `count`, `anyMatch`). Example shape: `tasks.stream().filter(t -> t.priority() == HIGH).map(Task::title).toList()`.
- **`Optional<T>`** — a return type meaning "may be absent". Spring Data's `findById` returns one. Use `orElseThrow(() -> new NotFoundException(...))`, `map`, `ifPresent`. Avoid `get()` and `isPresent()` + `get()`. Do not use `Optional` as a field or parameter type. (Day 46's "not-found path" test depends on this.)
- `java.time` in one line: `LocalDate.now()`, `due.isBefore(today)`.

**Exercise 3 (Must):** with `record Task(long id, String title, Priority priority, LocalDate due)` and a `List<Task>`:
(a) titles of HIGH-priority tasks, sorted; (b) count of overdue tasks; (c) `Optional<Task> findById(long)` over the list, and a caller that throws your own `NotFoundException extends RuntimeException` via `orElseThrow`; (d) map `List<Task>` → `List<TaskResponse>` (another record) using `TaskResponse::from`.

## 3. Part 2 — Day 31 (2.0 h + ≈1 h stretch): Spring core — IoC, DI, beans

*(Concepts kept from v1 Parts 1–4, tightened, with the corrections in Appendix C.)*

### 2.1 The problem and the idea — **Must** (35 min reading)

**Day 6 of Week 1** had you refactor `NotificationService` from `new EmailSender()` to constructor injection of a `MessageSender` by hand. Spring is that refactor, automated across the whole application.

- **IoC (Inversion of Control):** a class stops *creating* its collaborators and just *declares* what it needs. **DI (Dependency Injection):** the technique — collaborators are passed in from outside.
- **Three injection styles:** constructor (use this: fields can be `final`, no half-built objects, trivially testable — Day 46's `@InjectMocks` depends on it), setter (optional dependencies), field/`@Autowired` (seen in old code; hides dependencies — avoid). A class with exactly one constructor needs no `@Autowired`.
- **Bean:** an object whose creation and lifecycle the container manages. **`ApplicationContext`:** the container — at startup it finds bean classes, creates them in dependency order, injects them, and holds them until shutdown.
- **Default scope = singleton:** one instance *per container*, shared by every caller. Two consequences: (1) beans are created **eagerly at startup**, so wiring mistakes fail at startup, not on the first request; (2) a singleton is used by many request threads at once — **a mutable field in a bean is a concurrency bug** (Days 29/37 are why).
- **Stereotypes** — all register a bean; the name states the role: `@Component` (generic), `@Service` (business logic), `@Repository` (data access), `@RestController` (HTTP layer, returns JSON). `@Configuration` + `@Bean` method = a bean you define by hand, for classes you cannot annotate (a `Clock`, a `RestClient`, a Kafka template).
- **Component scanning:** Boot scans the package of your main class **and everything below it**. A controller in a sibling package is silently ignored → 404. Keep the main class at the root package.
- **`@SpringBootApplication` = `@Configuration` + `@EnableAutoConfiguration` + `@ComponentScan`.**
- **Choosing among beans:** type first; if several match, `@Primary` wins, then `@Qualifier("name")`, then — surprisingly — Spring falls back to matching the *parameter name* against bean names. Be explicit; do not rely on the fallback.
- **Config values:** `@Value("${app.greeting:Hello}")` injects a property (with a default after `:`). `@ConfigurationProperties` is the typed alternative once you have many (Day 51+).
- **Lifecycle hooks:** `@PostConstruct` runs once after injection; `@PreDestroy` on shutdown. Not used by name in this plan — recognize them, move on.
- **Spring Data repositories need no `@Repository`.** You write `interface TaskRepository extends JpaRepository<Task, Long>`; Spring generates the implementation at runtime (a dynamic proxy) and registers it.
- **Circular constructor dependencies** (A needs B needs A) fail at startup. Redesign; do not "fix" it with field injection.

## 4. Part 3 — Day 32 (3.5 h): Spring Boot and building REST endpoints

### 3.1 HTTP, JSON and `curl` in practice — **Must** (25 min)

- **Request** = method + path (+ query string) + headers + optional body. **Response** = status + headers + body.
- **Status codes you will actually use:** `200` OK, `201` Created (+ `Location` header), `204` No Content, `400` malformed or invalid request, `404` no such resource, `409` conflict with current state, `500` server bug. (Day 34's book also covers `422`.)
- **JSON ↔ Java:** object ↔ class/record, array ↔ `List`, string/number/boolean/`null` ↔ `String`/numbers/`boolean`/`null`.
- **Content-Type matters:** a POST body without `Content-Type: application/json` gets `415 Unsupported Media Type`.

```bash
curl -i localhost:8080/api/notes/1                                   # -i shows status line + headers
curl -i -X POST localhost:8080/api/notes \
     -H 'Content-Type: application/json' -d '{"title":"first","body":"hello"}'
```

### 3.2 What Boot does, and how a request travels — **Must** (25 min)

- **Auto-configuration is conditional:** Boot looks at the classpath and at beans you already defined, and configures what is missing — *backing off* wherever you define your own. See exactly what it decided: `java -jar app.jar --debug` (prints a conditions report).
- **Embedded Tomcat** handles each request on its own worker thread (hence §2.1's singleton warning).
- **Request path:** Tomcat → `DispatcherServlet` → handler mapping picks the controller method by (verb, path) → arguments are bound (`@PathVariable`, `@RequestParam`, `@RequestBody` via Jackson) → method runs → return value is written as JSON by an `HttpMessageConverter` → response. An exception on the way is routed to an `@ExceptionHandler` (Part 4).
- **`application.yml` basics:** `server.port`, `spring.application.name`, `logging.level.root`. **Precedence:** command-line args > environment variables > `application-{profile}.yml` > `application.yml`. **Env-var mapping:** `SERVER_PORT` ↔ `server.port`, `SPRING_DATASOURCE_URL` ↔ `spring.datasource.url` — this is how Kubernetes Secrets/ConfigMaps (Days 96, 136) override your yml.
- **Port busy?** `lsof -i :8080`, or set `server.port=8081`.

### 3.3 The Day 34 trap — read the error once, on purpose — **Must** (5 min)
Boot configures a `DataSource` the moment it sees Spring Data JPA plus a JDBC driver on the classpath. With no `spring.datasource.url` and no embedded database (e.g. H2), startup **fails fast**:

> `Failed to configure a DataSource: 'url' attribute is not specified and no embedded datasource could be configured.`

This is why Bridge Task A below changes Day 34's dependency list. Remember the message; you will meet it again.

### 3.4 Controllers, binding, responses — **Must** (30 min)

```java
@RestController
@RequestMapping("/api/notes")                       // shared base path
public class NoteController {
    private final NoteService service;
    public NoteController(NoteService service) { this.service = service; }

    @PostMapping
    public ResponseEntity<NoteResponse> create(@RequestBody CreateNoteRequest req) {
        NoteResponse created = service.create(req);
        return ResponseEntity.created(URI.create("/api/notes/" + created.id())).body(created);   // 201 + Location
    }

    @GetMapping("/{id}")                            // @PathVariable: WHICH resource
    public NoteResponse get(@PathVariable long id) { return service.get(id); }

    @GetMapping                                     // @RequestParam: filter / search / paginate OVER a resource
    public List<NoteResponse> list(@RequestParam(required = false) String contains) { return service.list(contains); }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> delete(@PathVariable long id) { service.delete(id); return ResponseEntity.noContent().build(); }
}
```
- `@RequestBody` = the payload of a POST/PUT/PATCH. Return a plain object for "200 + body"; return `ResponseEntity` when you must control the status or headers (`created`, `noContent`, `notFound`).
- **Idempotency (interview staple):** `GET`, `PUT`, `DELETE` are idempotent — repeating them leaves the same state; `POST` is not. `PUT` replaces the whole resource; `PATCH` changes part of it.
- `@Controller` (not `@RestController`) returns *view names*, not JSON — a classic first bug.

### 3.5 DTOs, not entities — **Must** (20 min)
Request and response types are **separate records** from your domain/entity class:
```java
public record CreateNoteRequest(String title, String body) {}
public record NoteResponse(long id, String title, String body) {
    static NoteResponse from(Note n) { return new NoteResponse(n.id(), n.title(), n.body()); }
}
```
Three reasons: (1) you do not leak internal fields; (2) clients cannot set fields they should not (`id`, `status` — "over-posting"); (3) your API stops being welded to your DB schema (Day 36 changes the entity, not the API). Jackson reads and writes records out of the box. A plain class returned from a controller needs getters, or Jackson throws `No serializer found … no properties discovered`.

### 3.6 Layering — **Must** (10 min)
**Controller** = HTTP only (binding, status codes). **Service** = business rules (and, from Day 41, transactions). **Repository** = data access. No `ResponseEntity` in a service; no business rule in a controller. This is Day 6's single-responsibility, applied.

### 3.7 Logging — **Must** (10 min)
```java
private static final Logger log = LoggerFactory.getLogger(NoteService.class);   // SLF4J ships with Boot
log.info("created note id={}", id);      // {} placeholders: not built unless the level is enabled
```
Levels: `ERROR`, `WARN`, `INFO` (default), `DEBUG`, `TRACE`. Never `System.out.println` in services. (Lombok's `@Slf4j` is only sugar for the line above — skip Lombok until you can write the boilerplate.)

## 5. Part 4 — Day 33 (2.5 h): Validation, errors, and the Day-34 gate

### 4.1 Bean Validation — **Must** (25 min)
Constraints live on the request record; `@Valid` on the parameter triggers them. (Day 34's Initializr list adds the Validation starter but nothing in the plan ever teaches it — this is it.)
```java
public record CreateNoteRequest(
        @NotBlank @Size(max = 100) String title,
        @Size(max = 1000) String body) {}

@PostMapping
public ResponseEntity<NoteResponse> create(@Valid @RequestBody CreateNoteRequest req) { ... }
```
Common constraints: `@NotBlank` (strings), `@NotNull`, `@Size`, `@Min`/`@Max`, `@Email`, `@FutureOrPresent` (dates). A failed `@RequestBody` validation raises `MethodArgumentNotValidException` → Spring answers `400` with a generic body. Constraints placed directly on `@PathVariable`/`@RequestParam` parameters (e.g. `@RequestParam @Min(1) int page`) are validated automatically on Spring 6.1+ and answer `400` (`HandlerMethodValidationException`); do **not** add `@Validated` to the controller class — that switches to the older AOP route with a different exception (`ConstraintViolationException`). Rule of thumb: **validate shape at the boundary (DTO); enforce invariants again where they truly matter (service/DB constraint)**.

### 4.2 One place for errors — **Must** (30 min)
```java
@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(NotFoundException.class)
    public ProblemDetail notFound(NotFoundException ex) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ProblemDetail invalid(MethodArgumentNotValidException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "Validation failed");
        Map<String, String> errors = new LinkedHashMap<>();
        ex.getBindingResult().getFieldErrors().forEach(fe -> errors.put(fe.getField(), fe.getDefaultMessage()));
        pd.setProperty("errors", errors);
        return pd;
    }
}
```
`ProblemDetail` is Spring's built-in error body (RFC 9457: `type`, `title`, `status`, `detail`, plus your own properties). Services throw a domain exception (`NotFoundException extends RuntimeException`); *only* this class knows about HTTP. **Design note:** Day 34 wraps `/health` in `ResponseWrapper<T>`. For CRUD, either return resources directly with correct status codes and use `ProblemDetail` for errors (the common REST style — the envelope would just repeat what the status already says), or wrap everything consistently. Pick one and be ready to defend it; Day 137's API-design exercise asks exactly this.

### 4.3 `@Transactional`, stated precisely — **Must** (10 min)
Runs a method inside one **database** transaction (one `DataSource`): all its writes commit together or none do. Precisely: it rolls back on **unchecked** exceptions (`RuntimeException`, `Error`) by default — **not** on checked ones unless you set `rollbackFor`. It works through a **proxy**, so calling a `@Transactional` method from another method *in the same class* bypasses it. And it does **not** cover a Kafka send: a DB commit and a message publish are two systems, so "save the order, then publish `OrderCreatedEvent`" can lose either half (the dual-write problem — Later 4 in §6). First needed: Day 41. `@Transactional(readOnly = true)` for reads.

### 4.4 Testing, previewed — *Stretch* (15 min; real work is Day 45)
Three shapes: plain JUnit (no Spring); **`@WebMvcTest` + `MockMvc`** (controller slice, services mocked); **`@SpringBootTest`** (whole context). `@DataJpaTest` is for *repositories* — it does not load controllers.
```java
@WebMvcTest(NoteController.class)
class NoteControllerTest {
    @Autowired MockMvc mockMvc;
    @MockitoBean NoteService service;                    // Boot 3.x: @MockBean

    @Test void missingNoteIs404() throws Exception {
        when(service.get(99L)).thenThrow(new NotFoundException("note 99"));
        mockMvc.perform(get("/api/notes/99")).andExpect(status().isNotFound());
    }
}
```

## Appendix B — First-week error decoder

| You see | Usual cause | Fix |
|---|---|---|
| `Failed to configure a DataSource: 'url' attribute is not specified` | JPA + driver on classpath, no datasource config | remove them (Day 34) or configure the datasource (Day 36) |
| `Port 8080 was already in use` | another app running | `lsof -i :8080`; stop it or `server.port=8081` |
| `Parameter 0 of constructor … required a bean of type …` | missing stereotype annotation, or class outside the scanned package | annotate it; move it under the main class's package |
| `NoUniqueBeanDefinitionException` | two beans implement the same interface | `@Primary` or `@Qualifier` |
| `404` on an endpoint you mapped | controller not scanned; wrong path; `@Controller` instead of `@RestController` | check package, path, annotation |
| `415 Unsupported Media Type` | POST without `Content-Type: application/json` | add the header |
| `400` + `HttpMessageNotReadableException` | malformed JSON or wrong type for a field | fix the body |
| `No serializer found for class … no properties discovered` | returning a class with no getters | use a record, or add getters |
| `UnsatisfiedDependencyException` mentioning a cycle | circular constructor dependency | redesign the dependency direction |
| `package javax.…` / `com.fasterxml.jackson.databind` does not exist | copied an old tutorial | `jakarta.*`; Jackson 3 is `tools.jackson.*` on Boot 4 |

## Appendix C — Corrections to the v1 primers
1. "Week 6, Day 6" (three places) → the SOLID / Dependency Inversion exercise is **Week 1, Day 6**.
2. "Day 68's autocomplete" (two places) → autocomplete is **Day 59**; Day 68 is graphs + rate limiting.
3. `@Repository` on a `JpaRepository` interface is unnecessary — Spring Data registers repository interfaces itself and applies exception translation.
4. `@Transactional` rolls back on *unchecked* exceptions by default, not "if anything throws"; self-invocation bypasses it (§4.3).
5. v1 Part 10's Day 48 bullet implies `@Transactional` covers "save + publish to Kafka". It does not (dual-write → outbox).
6. v1 Part 7 says Boot "just configures" a `DataSource` from JPA + a driver. Without `spring.datasource.url` it **fails at startup** — the exact cause of the Day 34 break (§3.3).
7. `spring-boot-starter-web` is `spring-boot-starter-webmvc` on Boot 4 (§1).
8. v1 Part 5 binds `@RequestBody` straight to the `Task` entity — use request DTOs (§3.5).
9. Maven micro-primer: "dependencies by name and version" → Initializr poms have no starter versions; `mvn` is not installed — use `./mvnw`; `package` yields a runnable jar only because of the Boot plugin.
