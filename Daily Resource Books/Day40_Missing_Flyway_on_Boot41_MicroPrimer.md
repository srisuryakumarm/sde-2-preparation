## 1. Dependencies on Boot 4.x
Boot 4 gives Flyway its own starter, and Flyway 10+ needs a database-specific module:
```xml
<dependency><groupId>org.springframework.boot</groupId><artifactId>spring-boot-starter-flyway</artifactId></dependency>
<dependency><groupId>org.flywaydb</groupId><artifactId>flyway-database-postgresql</artifactId></dependency>
```
(On Boot 3 it was `flyway-core` plus the same Postgres module.) Configuration keys (`spring.flyway.enabled`, `spring.flyway.locations`) are unchanged. Migrations live in `src/main/resources/db/migration/V1__create_tasks_table.sql` (two underscores).

## 2. The trap: Hibernate already created `tasks` on Day 36
Running `V1__create_tasks_table.sql` against that database fails with `relation "tasks" already exists`. Day 40's own definition of done says "a fresh database with no prior schema comes up correctly from the migration alone" — so give it one:
- Docker: `docker rm -f todo-postgres`, then re-run Day 36's `docker run`. Native: `dropdb tododb && createdb -O postgres tododb`.
- Switch to `ddl-auto: validate`, start the app, and check `flyway_schema_history` shows `V1`.

## 3. Make `validate` happy
`validate` compares your entity to the real schema and refuses to start on a mismatch. Write the migration to match the entity: `BIGINT GENERATED BY DEFAULT AS IDENTITY` for the id (with `GenerationType.IDENTITY`), `VARCHAR` for enums stored with `EnumType.STRING`, `DATE` for `due_date` (Hibernate maps `dueDate` → `due_date`). A message like `wrong column type encountered in column [status]` means fix the **migration**, not the entity.
